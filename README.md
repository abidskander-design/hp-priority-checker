# HP+ Priority Checker

A Chrome extension and local Flask backend that predict whether an OpenStack
Gerrit change should receive the **Review-Priority HP+** label, and explain
the prediction in plain technical language with a large language model.

[![HP+ Priority Checker demo video](https://img.youtube.com/vi/Fg72RMNByP4/hqdefault.jpg)](https://www.youtube.com/watch?v=Fg72RMNByP4)

▶ **Tool demonstration (ICSE 2027):** https://www.youtube.com/watch?v=Fg72RMNByP4

## Features

- **Dashboard badges** – on a review.opendev.org change list, every visible
  change of a supported project gets a 🔴 **HP+** or 🟢 **Normal** badge, so
  reviewers can spot urgent changes without opening them. All visible changes
  are sent in a single batch request, and results are cached for 5 minutes.
- **Change banner** – opening a change shows a banner with the verdict, the
  HP+ probability, the decision threshold and the detected category
  (bug fix, feature, CI, docs, release/maintenance).
- **LLM explanation** – the popup shows a structured explanation
  (*Verdict*, *Key Signals*, *Why It Matters*, *Suggestion*) generated by an
  NVIDIA NIM model (`nemotron-3.5-lightning-30b-a3b` by default, see
  [Configuration](#configuration)). It is grounded in the commit message,
  changed files and recent reviewer comments, and the prompt asks every
  section to agree with the model's verdict.
- **Risk dashboard** – the most influential model features.
- **Settings** – switch between the G-mean, F0.5 or a custom threshold
  without retraining.
- **History** – every prediction is stored in a local SQLite database.

## How it works

```
review.opendev.org
  └─ content.js  (detects list / change pages, injects badges + banner)
       └─ background.js  ──HTTP──►  Flask backend  (127.0.0.1:5487)
                                     ├─ gerrit_client.py     Gerrit REST API
                                     ├─ feature_extractor.py change → features
                                     │    + author history from SQLite
                                     ├─ predictor.py         per-project XGBoost
                                     ├─ llm_explainer.py     NVIDIA NIM
                                     └─ db.py                prediction log
```

## Supported projects

One XGBoost model is trained per project:

| Project               | HP+ rate in training data | G-mean threshold | F0.5 threshold |
|-----------------------|--------------------------:|-----------------:|---------------:|
| `openstack/nova`      |  1.7 % | 0.930 | 0.930 |
| `openstack/neutron`   |  4.8 % | 0.715 | 0.850 |
| `openstack/cinder`    |  8.9 % | 0.738 | 0.848 |
| `openstack/glance`    | 13.7 % | 0.938 | 0.938 |
| `openstack/designate` | 13.3 % | 0.880 | 0.880 |

## Requirements

- Google Chrome or Chromium
- **Either** Docker (or Podman) **or** Python 3.14
- Optional: an NVIDIA API key for NIM ([build.nvidia.com](https://build.nvidia.com)).
  Without it, predictions still work and the popup shows
  "LLM explanation unavailable".

## Quick start

1. **Get the code**

   ```bash
   git clone https://github.com/abidskander-design/hp-priority-checker.git
   cd hp-priority-checker
   ```

2. **Optional – API key**: copy `.env.example` to `.env` and put your key in it.

3. **Start the backend** (one of the two):

   - **With Docker** (recommended):

     ```bash
     docker compose up --build        # or: podman-compose up --build
     ```

   - **Without Docker** (Python 3.14):

     ```bash
     ./start_backend.sh
     ```

   Either way the API runs on `http://127.0.0.1:5487`. Check it with:

   ```bash
   curl http://127.0.0.1:5487/health
   ```

4. **Load the extension** – open `chrome://extensions`, enable
   **Developer mode**, click **Load unpacked** and select the `extension/`
   folder.

5. **Use it** – open the open-changes list of a supported project, e.g.
   https://review.opendev.org/q/project:openstack/neutron+status:open,
   or any change of a supported project, then click the extension icon to see
   the explanation.

## Configuration

Set these in `.env` (or as environment variables):

| Variable          | Default                                  | Meaning |
|-------------------|------------------------------------------|---------|
| `NVIDIA_API_KEY`  | –                                        | NVIDIA NIM key; without it, no LLM explanation |
| `NVIDIA_MODEL`    | `nvidia/nemotron-3.5-lightning-30b-a3b`  | LLM used for explanations (~3–6 s per change) |
| `NVIDIA_THINKING` | `0`                                      | `1` enables reasoning mode, e.g. with `nvidia/nemotron-3-ultra-550b-a55b` (15–50 s, follows the verdict more closely) |
| `HP_CHECKER_PORT` | `5487`                                   | Backend port (the extension expects 5487) |

The original model, `nvidia/llama-3.3-nemotron-super-49b-v1`, was retired by
NVIDIA on 2026-08-26.

## Backend API

| Method | Endpoint         | Description |
|--------|------------------|-------------|
| POST   | `/predict`       | Full prediction + LLM explanation for one change. Body: `{"change_id": "12345", "project": "openstack/nova", "threshold_type": "gmean" \| "f05", "threshold_override": 0.8}` |
| POST   | `/predict_batch` | Verdicts for up to 50 changes (no LLM). Body: `{"changes": [{"change_id": "...", "project": "..."}]}` |
| GET    | `/history`       | Latest predictions (`?limit=50`) |
| GET    | `/latency`       | Prediction latency statistics |
| GET    | `/projects`      | Supported projects |
| GET    | `/health`        | Health check |

## Retraining the models

```bash
python scripts/train_models.py
```

This reads `../review-priority-predictor/data/processed/dataset_with_subjects.csv`
from the companion research repository (the dataset is not included here),
trains one XGBoost model per project, and writes `backend/models/*.joblib`
together with `backend/models/manifest.json` (thresholds and HP+ rates).
Running the tool does **not** need the dataset: the trained models and the
author-profile database are included.

## Evaluation

The `train_auc` values in `backend/models/manifest.json` are in-sample (each
model is scored on its own training data) and are not a measure of accuracy.
A held-out, time-aware evaluation of the same pipeline (trained on changes
before 2024-01-01, tested on all changes from 2024-01-01 on) is in
[`evaluation/holdout_results.md`](evaluation/holdout_results.md). It can be
reproduced with the research dataset:

```bash
python scripts/evaluate_holdout.py
```

On held-out data, submission-time prediction is weak (mean ROC-AUC 0.59, mean
MCC 0.09 at the G-mean threshold), so the tool is meant as decision support
for triage rather than as an automatic gatekeeper.
